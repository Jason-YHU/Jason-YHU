13.1 User-Defined Data Types

Your notes don't explain why user-defined types exist — worth knowing since it's an explicit syllabus point:
Why user-defined types are necessary Built-in types (INTEGER, STRING, CHAR, etc.) don't always model real-world data well on their own. User-defined types let you combine or restrict them to match the actual problem — e.g. representing "one of four seasons" or "a book with several fields of different types" precisely, rather than working around it with generic types.

Sets

Definition A collection of data that lacks any structure (unordered) and contains no duplicates. A fixed number of standard operations can be performed on it.
Declaring a set type TYPE <set-identifier> = SET OF <base type>
Example TYPE SLetter = SET OF CHAR
DEFINE vowel ('a','e','i','o','u') : SLetter

Using DEFINE setA ('a','b','c') : SLetter and DEFINE setB ('b','c','d') : SLetter as running examples:

Union / Intersection / Difference / Membership setA ∪ setB → {a,b,c,d}  ·  setA ∩ setB → {b,c}  ·  setA − setB → {a}  ·  IF 'a' IN setA THEN … → TRUE
Adding / removing values Add one value: setA ← setA ∪ {'d'}  ·  Remove one value: setA ← setA − {'a'}  ·  Add a whole set: setA ← setA ∪ setB

1. Is a pointer a composite or non-composite type?
Non-composite — it's built from only one underlying type (an address).

4. Why might a record be a better choice than several separate variables for storing one student's name, age, and grade?
The related fields are grouped under one identifier, so they can be passed around and processed together (e.g. as one array element per student) instead of managing several parallel variables.
5. What's the key difference between a record and a class?
A record stores only data (fields); a class also bundles in the methods (procedures/functions) that operate on that data.

13.2 File Organisation & Access

File organisation — how records are stored

SerialSequentialRandom
Records added one by one, in the order they arrive. Records kept in order, based on a key field. Records stored in any available position, located later using a record key.

File access — how records are retrieved

Sequential accessDirect access
Travel through records one by one from the start, checking each one, until the target is found (or, for an ordered file, until the value checked exceeds the target — meaning it can't exist further on). Works for serial and sequential files. Jump straight to the record without checking every one before it. Works for sequential (via an index) and random (via hashing) files.
Worksheet practice — matching organisation to access
OrganisationValid access method(s)
RandomDirect (only)
SerialSequential (only)
SequentialSequential or Direct (via an index)
Worksheet practice — choosing an organisation for a scenario File A needs records read in arrival order only → Serial.
File B needs records kept in a defined order → Sequential.
File C needs the fastest possible access speed → Random (direct access).
The syllabus explicitly wants you to describe and use a hashing algorithm — your notes only say "use a hashing algorithm" without one:
Hashing algorithm A calculation that converts a record's key directly into a storage address, so the record can be found without searching.
Simplest method — division/remainder (modulo)
address = record key MOD number of storage locations
Worked example 10 storage locations (addresses 0–9). Record key = 1023.
1023 MOD 10 = 3 → the record is stored at (or looked up from) address 3.
Collisions Two different keys can hash to the same address (e.g. 1013 MOD 10 = 3 too) — this is a collision. A common fix is to store the second record in the next free slot (linear probing) and search forward from the "expected" address if it's not there when retrieving.
Self-testWhich organisation type must be used with direct access only?
Random — sequential files can use direct access too, but only via an index.
Self-testWhy can sequential access stop early on an ordered file?
Because the records are sorted — once you pass where the target would be, it can't appear later.

47 MOD 10 = 7

Quiz — 13.2 File Organisation & Access

1. A file only ever needs its records read from start to end, never jumped into midway. Which organisation is simplest and sufficient?
Serial.
2. Using key MOD 8 with 8 storage locations, where does key = 29 hash to?
29 MOD 8 = 5
3. What is a collision in the context of hashing?
When two different keys hash to the same storage address.
4. Why does a sequential file need an index to support direct access, when a random file doesn't?
A random file's address comes straight from hashing the key; a sequential file's physical position doesn't relate to the key directly, so a separate index (key → position) is needed to jump to it.
5. Which is faster on average for finding one specific record: sequential access or direct access?
Direct access — it jumps straight to the record instead of checking records one by one.

13.3 Floating-Point Numbers

high-yield
Definition A floating-point number is stored as two parts: the mantissa (M), which holds the significant digits, and the exponent (E), which says how far to shift the binary point. Both are stored as fixed-length two's complement binary strings.
Formula
value = M × 2E

Binary → Decimal

Shift the mantissa's point right by E places if E is positive (left if E is negative), then convert to decimal.

Worked example — positive number M = 0.1011010, E = 00000100 (= 4)
Shift right by 4: 1011.010 = 8+2+1+0.25 = 11.25
Worked example — negative mantissa M = 1.1110100 (MSB = 1, negative), E = 00000100 (= 4)
Magnitude: invert + 1 → 0.0001100, shift right 4: 0001.100 = 1.5 → −1.5
Worksheet practice — large positive exponent M = 0.1110010, E = 00000111 (= 7)
Shift right by 7: 01110010. = 64+32+16+2 = 114

Decimal → Binary

  1. Convert the whole-number part and fractional part to binary separately, and combine.
  2. Normalise so the point sits in the required position — count how many places you shift it.
  3. Adjust E by that many places, then write M and E as fixed-length two's complement binary.
Worked example — 4.5 4 = 0100, 0.5 = .1 → 0100.1
Normalise: move point left 3 → 0.1001, E increases by 3
M = 0.1001000, E = 00000011
Worked example — pure fraction, 0.375 0.375 = 3/8 = 0.011 = 0.11 × 2−1
M = 0.11, E = −1 (two's complement 11111111)

Normalise the positive magnitude first: move point left 4 → 0.1000011, E = 4 (00000100)
To negate, two's-complement the whole 8-bit mantissa (sign bit included, not just the fraction part): invert 01000011 → 10111100, add 1 → 10111101
M = 1.0111101, E = 00000100
The subtle bit It's tempting to two's-complement only the fractional digits and leave the leading bit as 0 — that gives a mantissa starting "0.1…", which looks like a positive pattern and is wrong. The sign bit must be included in the invert-and-add-1 step.

Normalisation

Rule A mantissa is normalised when its first digit after the point differs from the sign bit:
Positive number01…
Negative number10…
Shift rule Moving the point left one place → E increases by 1. Moving it right → E decreases by 1.
Why normalise? (two reasons) 1. It gives every number exactly one valid representation — without it, the same value could be written many different ways, which is ambiguous.
2. It maximises precision, using every available mantissa bit for significant digits instead of wasted leading 0s/1s.

Edge case worth knowing: zero itself cannot be written in strictly normalised form (0.0000000 doesn't satisfy either pattern above) — it's the one value systems must special-case.

Precision versus Range

Key trade-off More mantissa bits → greater precision. More exponent bits → greater range.

e.g. for high accuracy but low range: allocate a large mantissa and a small exponent (and vice versa for high range but low accuracy).

CaseMantissaExponent
Largest positive number0 111111101111111 (E = +127)
Smallest positive number0 100000010000000 (E = −128)
Largest-magnitude negative number1 000000001111111 (E = +127)
Smallest-magnitude negative number1 011111110000000 (E = −128)
Your notes don't cover the limitations of floating-point representation — a syllabus point on its own:
Approximation & rounding errors Not every real number can be represented exactly in binary floating point — e.g. 0.1 in binary is a recurring fraction (0.0001100110011…). Since only a fixed number of mantissa bits are available, the stored value must be rounded to the nearest one that fits, creating a small rounding error between the true value and what's actually stored.
Overflow Occurs when a number's magnitude is too large to be represented, even using the largest available exponent.
Underflow Occurs when a number's magnitude is too small (too close to zero) to be represented, even using the smallest available exponent — it effectively rounds down to zero.
Self-testWhy does E increase by 3 in the 4.5 example?
Moving the point left makes M smaller, so E must rise to keep M × 2E equal to 4.5.

One unique representation per value, and maximum precision.

Quiz — 13.3 Floating-Point Numbers

1. M = 0.11, E = 00000010 (=2). Find the decimal value.
Shift right 2: 11.0 = 3
2. Why can't 0.1 (decimal) be stored exactly in binary floating point?
Its binary representation is a recurring fraction, so a finite number of mantissa bits can only store an approximation, not the exact value.
3. Is 0.0110100 (positive) normalised?
No — the digit right after the point must be 1 for a positive number.
4. You need to represent much bigger numbers with the same total bit budget. Which field should grow?
The exponent (at the cost of precision, since the mantissa would need to shrink).
5. A number is too large to fit even with the maximum exponent. What is this called?
Overflow.
